# Blocks, Attributes, And Motion

This document defines the MDS extension model.

The short version:

**Everything extensible is a block. Custom components are blocks. Motion is also a block.**

MDS does not need a separate animation runtime or component runtime. It needs a general block AST, optional block attributes for advanced authors, and themes that turn those blocks into standalone HTML, CSS, and JavaScript.

## Principles

- MDS core parses structure and intent.
- Themes own presentation, animation, and component implementation.
- The final output is still standalone HTML.
- Block attributes are supported, but ordinary content should prefer semantic block names and slots.
- Unknown blocks should remain renderable through safe fallback HTML and diagnostics.
- MDS documents must not embed arbitrary JavaScript handlers.

## Block Model

Every MDS block has the same shape:

```ts
type BlockNode = {
  type: string;
  name?: string;
  id?: string;
  attrs: Record<string, string | number | boolean>;
  slots: SlotNode[];
  children: Node[];
};
```

Examples:

```mds
::: hero landing motion="fade-up" tone="dark"
# Launch faster
:::
```

```txt
type: hero
name: landing
id: landing
attrs:
  motion: fade-up
  tone: dark
```

```mds
::: data-table releases page-size=20 selectable
## Releases
Recent package versions.
:::
```

```txt
type: data-table
name: releases
id: releases
attrs:
  page-size: 20
  selectable: true
```

## Names, IDs, And Display Titles

The optional token after the block type is a stable reference id, not the human-readable title.

```mds
::: section product-intro
# Product Intro!
:::
```

```txt
type: section
name: product-intro
id: product-intro
display title: Product Intro!
```

This keeps block openers easy to parse even when titles contain spaces, punctuation, emoji, or non-Latin text. Human-readable titles should come from normal Markdown content:

```mds
::: section
# 产品介绍
:::
```

If no explicit name is provided, the renderer should derive an id from the first heading or title slot using a Markdown-like slug algorithm:

```txt
Product Intro! -> product-intro
产品介绍 -> 产品介绍
产品介绍 -> 产品介绍-2
```

Slug rules should be deterministic and shared by parser/renderer/editor tooling:

- Strip Markdown formatting from the source heading.
- Trim surrounding whitespace.
- Lowercase ASCII letters.
- Replace whitespace runs with `-`.
- Remove punctuation that is unsafe in HTML ids or URL hashes.
- Preserve Unicode letters and numbers.
- Collapse repeated dashes.
- Deduplicate later ids with `-2`, `-3`, and so on.

Explicit names are still recommended for blocks targeted by actions or long-lived links:

```mds
::: details faq
# Frequently Asked Questions
:::

[Toggle FAQ !toggle faq]
```

Do not quote natural-language names in the opener:

```mds
::: section "Product Intro!"
```

Quoted names would collide with attribute parsing and make action targets less predictable. Use a heading for display text and a short id for references.

## Attribute Syntax

Supported forms:

```mds
::: card variant=featured
::: card variant="featured"
::: card variant='featured'
::: card featured
::: grid columns=3 gap=24
```

Rules:

- Attribute names use simple identifier syntax: letters, numbers, `_`, `-`, and `:`.
- Values can be unquoted or quoted.
- Boolean flags become `true`.
- Number-looking values may be normalized to numbers in the AST.
- Attribute order should be preserved for formatting tools, but rendering should not depend on order.
- Curly attribute syntax is not part of MDS: `::: card {variant=featured}`.
- Event-handler attributes such as `onclick` and script URLs such as `javascript:` are unsafe and should produce diagnostics instead of executable output.

## Authoring Guidance

Prefer semantic blocks:

```mds
::: warning
Dangerous action.
:::
```

Use attributes when the theme explicitly exposes component variants:

```mds
::: alert tone="warning"
Dangerous action.
:::
```

Prefer slots for structured content:

```mds
::: hero
--- title
# Build with MDS

--- actions
[Start -> /start]
:::
```

Use attributes for compact configuration, not large content payloads.

## Theme Contract

Themes receive the block as data and decide what to do with it:

```tsx
hero: (block) => (
  <Root block={block} className={`hero tone-${block.attr("tone", "default")}`}>
    <Content block={block} />
  </Root>
)
```

Template themes can consume attributes through placeholders:

```html
<section{{ attrs }} class="hero hero-{{ attr:tone }}">
  {{ children }}
</section>
```

The `{{ attrs }}` placeholder is for safe root attributes generated by the renderer, such as `id` and sanitized theme-facing attributes. Themes should not blindly turn all MDS attributes into browser attributes unless the loader marks them safe.

## Motion As Blocks

Motion is not special syntax. A motion wrapper is just a block:

```mds
::: motion preset="fade-up" trigger="view" stagger=80
::: card
## One
:::

::: card
## Two
:::
:::
```

A theme might render it as:

```html
<div data-motion="fade-up" data-trigger="view" style="--stagger:80ms">
  ...
</div>
```

The theme JavaScript can then implement the behavior with CSS, `IntersectionObserver`, Web Animations API, Motion One, GSAP, or any other library. MDS core does not care.

The three shared motion blocks have intentionally different scopes:

| Block | Meaning | Use it for |
| --- | --- | --- |
| `motion` | Group choreography. | Multiple child blocks that share a preset, especially staggered cards or list items. |
| `reveal` | One-region reveal. | A single content region that should enter as one visual unit. |
| `scene` | Visual staging surface. | A distinct editorial section whose `variant` changes atmosphere; it is not a timeline or animation engine. |

These blocks preserve intent only. A theme may implement them with different visual language, or render all content without motion when reduced motion is requested.

## Motion As Component Attributes

Themes can also let normal blocks opt into motion:

```mds
::: hero motion="fade-up" delay=120
# Hello
:::
```

This is still theme behavior. MDS does not define the meaning of `fade-up` or `delay`.

Recommended baseline motion attributes:

```txt
motion   preset name
trigger  load | view | hover | state
delay    milliseconds
duration milliseconds
stagger  milliseconds between children
once     boolean
```

These names are conventions for theme interoperability, not required core semantics.

## Unknown Blocks

Unknown blocks are expected in an extensible system.

If the selected theme has a matching template, render it. If not, renderer fallback should preserve the block:

```html
<section class="block x-widget" data-block="x-widget">
  ...
</section>
```

The renderer should emit a warning so the editor can explain that the selected theme does not implement the block.

## Implementation Plan

1. Extend AST block nodes with `attrs`.
2. Parse block attributes after type and optional name.
3. Add diagnostics for invalid or unsafe attributes.
4. Expose `attrs`, `attr(name)`, and safe root attribute helpers to templates and SDKs.
5. Update HTML renderer fallback to preserve unknown block type, name, and safe attrs.
6. Add Canvas `motion` block and component-level `motion` attrs.
7. Add examples for custom components, motion wrappers, and advanced attrs.
8. Add tests for parsing, rendering, diagnostics, SDK helpers, and standalone theme behavior.
